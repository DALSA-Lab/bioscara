\doxysubsection{Detailed Description}
The bioscara arm hardware interface class. 

The hardware interface serves to wrap custom hardware interaction with the arm joints in the standardized ros2\+\_\+control architecture.

{\bfseries{Hardware Lifecycle}} ~\newline
The hardware follows the ros2\+\_\+control hardware interface lifecyle which intern is following the \href{https://github.com/ros2/design/blob/93a415bf928751d37fce6f83215c521658e20c93/articles/node_lifecycle.md}{\texttt{ ROS2 managed node lifecycle}}.

Called on the transistion from the {\ttfamily inactive} to the {\ttfamily active} state. 

Calls \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_aacfb3f227b2e2e5ab0d4aaa6e6790771}{activate\+\_\+joint()} to enable the joints. ~\newline
It is allowed to activate the hardware even if it is not homed. To home the joint the homing\+\_\+controller must be activated, but generally a hardware component must be active in order for controllers to become active. ~\newline
 To prohibit movement on activation the set point for each position command interface is set equal to the current measured position, and the velocity command is set to 0.\+0 for each command interface. The current values are obtained by calling the \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_adc34f1df847375abf18fe8100ecec1d1}{read()} method once which populates the state interfaces with values.

Called when an error in any state or state transition is thrown. 

According to the \href{https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/hardware_components_userdoc.html\#handling-of-errors-that-happen-during-read-and-write-calls}{\texttt{ ros2\+\_\+control documentation}}\+:

\begin{quote}
Error handling follows the node lifecycle. Performs checks and book keeping of the active control mode when changing controllers in non-\/realtime context. 

For safe operation only one controller may interact with the hardware at the time. For example if the velocity JTC is active and has claimed the velocity command interfaces it is technically possible to activate the position JTC (or a homing controller, or others) that claim a different command interface (position in this case). However if both controllers are active they start writing to the hardware simultaneously which is to be avoided. For this reason a book keeping mechanism has been implemented which stores the currently active command interfaces for each joint in the \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_afc419a32f050cf461e64d958fed917ce}{\+\_\+joint\+\_\+command\+\_\+modes} member. Each joint has a set of active command interfaces. When a controller switch is performed the interfaces that should be stopped are removed from each joint set, then the one that should be started are added, if they are already present an error is thrown. Lastly a validation is performed. Currently the validation is simple since each joint may only have one command interface. The validation can be expanded for furture use cases that require a combination of active command interfaces per joint for example. ~\newline
 The following basic checks are implemented\+:
\begin{DoxyItemize}
\item {\bfseries{On deactivation}}\+:
\begin{DoxyItemize}
\item \mbox{[}ERROR\mbox{]} Homing command interfaces may only be deactivated if no current homing process is ongoing (\doxylink{classbioscara__hardware__drivers_1_1BaseJoint_a412c4e474be5de0820d88b7d1d6084de}{bioscara\+\_\+hardware\+\_\+drivers\+::\+Joint\+::get\+Current\+BCmd()} != \doxylink{classbioscara__hardware__drivers_1_1BaseJoint_affbc9ba6c17b02af32647dc76796de13a93a9a074f04be4b2316dbbca5882b6fa}{bioscara\+\_\+hardware\+\_\+drivers\+::\+Joint\+::\+HOME})
\item \mbox{[}WARN\mbox{]} Deactivating a velocity command interface if the velocity set point is 0.\+0.
\item \mbox{[}WARN\mbox{]} Deactivating a command interface that has not been started. This should not happen.
\end{DoxyItemize}
\item {\bfseries{On activation}}\+:
\begin{DoxyItemize}
\item \mbox{[}ERROR\mbox{]} Activating a command interface that is already started. This should not happen.
\item \mbox{[}ERROR\mbox{]} Activating a second command interface for a joint.
\item \mbox{[}ERROR\mbox{]} Activating \textquotesingle{}position\textquotesingle{} or \textquotesingle{}velocity\textquotesingle{} command interface if the joint is not homed (\doxylink{classbioscara__hardware__drivers_1_1BaseJoint_ad010a69043a9ee4578cadeebc85d9c80}{bioscara\+\_\+hardware\+\_\+drivers\+::\+Joint\+::is\+Homed()} == false).
\end{DoxyItemize}
\end{DoxyItemize}Since this method operates in non-\/realtime context it must not access critical members (\doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_afc419a32f050cf461e64d958fed917ce}{\+\_\+joint\+\_\+command\+\_\+modes} and \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_a99e93a65247944cf62e75767ba98a656}{\+\_\+joints}) to avoid priority inversion. Therefore the new command modes are first saved to a cache \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_a222af12f49df8ea14f9d0d44a92e9617}{\+\_\+new\+\_\+joint\+\_\+command\+\_\+modes}. This will then be applied to \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_afc419a32f050cf461e64d958fed917ce}{\+\_\+joint\+\_\+command\+\_\+modes} in the \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_a06406f562da286f933b52b6e7009bd7f}{perform\+\_\+command\+\_\+mode\+\_\+switch()} which is executed in RT context.

The mutex prevents two things\+:
\begin{DoxyItemize}
\item Modifying the \doxylink{classbioscara__hardware__interfaces_1_1BioscaraArmHardwareInterface_afc419a32f050cf461e64d958fed917ce}{\+\_\+joint\+\_\+command\+\_\+modes} concurrently.
